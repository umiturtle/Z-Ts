# ADR-0019: API リファレンスはソースから生成し、サイトの主役を「使う人向け」に振り直す

- **Status**: Accepted
- **Date**: 2026-10-30
- **Related**: [`0018-documentation-site.md`](0018-documentation-site.md) /
  [`../architecture/documentation-site.md`](../architecture/documentation-site.md) /
  [`../tasks/M5-07-api-reference.md`](../tasks/M5-07-api-reference.md)

## 1. 背景

ADR-0018 でドキュメントサイトを作ったとき、サイトは**リポジトリの写像**だった。
`docs/` のファイルをそのまま並べたので、サイドバーには ADR 18 本・タスクシート 25 本が
「はじめに」のすぐ隣に並び、検索もそれらを等しく返していた。

出来上がってみると、読者の最初の質問（「`Schema` はどう書くの？」「署名は？」）に答える場所が
**どこにも無かった**。ソースを GitHub で開くしかなく、それはドキュメントではない。

## 2. 決定

### 2.1 サイトの主役は「使う人向け」、実装意図は畳む

サイドバーは次の 5 グループだけにする。

```
はじめに（README / ドキュメント索引）
ガイド（getting-started / using-* / migrating-from-tauri / troubleshooting / cli）
API（全体索引 + 10 パッケージ）
サンプル（examples/*/README）
内部資料（1 エントリだけ → docs/internals/index.html）
```

* ADR・タスク・設計メモ・ロードマップ・環境ノート・`AGENTS.md` は **`内部資料` の 1 エントリ**に畳む。
  個別ページは**公開したまま**（他のページからリンクされている）が、サイドバーには並べない。
* 内部ページには上部に **「内部資料」バナー**を出し、読者向けドキュメントへのリンクを置く。
* **検索インデックスから内部資料を除外**する。検索は読者のための機能で、
  「M3-02 の当時の判断」を探す場所ではない。
* `docs/internals/index.html` が全内部資料をティーザー付きで一覧する（行き止まりを作らない）。

### 2.2 API リファレンスは Zig ソースから生成する

`src/docsite/apidoc.zig` が各パッケージの**相対 import グラフ**を辿り、次を HTML にする。

* モジュールの `//!` ドキュメント（Markdown として描画）
* トップレベルの `pub` 宣言すべて（`fn` / `const` / `var` / 型）
* 型本体の**メンバ**（Zig の struct フィールドは `pub` を書かないので、別判定で拾う）
* 宣言ごとの `///` ドキュメント、**ソース行へのリンク**、シグネチャの色分け

出力は 3 層（全体索引 / パッケージ / モジュール）で、モジュールページの URL は
**パッケージ内の相対パス**（`docs/api/zts_tauri/tray/mod.html`）。
`mod.zig` は 1 パッケージに 6 個あり得るので、basename を使ってはいけない。

### 2.3 読者の学習面と内部実装を分ける

API ページは全ファイルを生成するが、**索引・検索・文書化率には公開モジュールだけ**を載せる。

* `gtk_bindings.zig`（69 宣言）・`win32.zig`（142）・`webview2_com.zig`（63）は手書きの `extern`
  テーブルで、読者が学ぶ対象ではない。`<details>` に折り畳み、ページ先頭に「内部実装」バナーを出す。
* 文書化率の分母からも外す。`///` を `HWND_TOPMOST` に貼らせる圧力を作らないため。
* 除外件数は `api_internal=…` としてログに出す（隠していないことを検証できる）。

ガイド・仕様・内部資料の 4 層の役割分担は
[`../guides/README.md`](../guides/README.md) §2 に正本を置いた。

### 2.4 リンク検査に「アンカー」を足す

`#Schema` が存在しない宣言を指していても、これまではファイルが存在すれば通っていた。
`verifyAssets` が出力ツリーの**全 `id=` を先に収集**し、`page.html#anchor` の
アンカー実在まで検査するようにした（`error.DanglingAnchors`）。

## 3. 検討した代替案

1. **`zig build-lib -femit-docs`（Zig 標準の autodoc）をそのまま同梱**
   — 本物の `zig doc` が出るが、wasm + 専用 JS の単体アプリで、サイトの外観・検索・
   リンク検査・`_site` の相対化と統合できない。**却下**。
2. **`docs/api/*.md` を手で書く** — 2,500 件の宣言を手で維持することは不可能で、
   必ずソースとずれる。**却下**。
3. **内部資料を削除 / `robots.txt` で遮断** — 設計の経緯は他のエージェントと将来の自分に
   必要な資産で、削除は損失。`noindex` も、リンクで直接来た読者を弾くだけで意味が薄い。
   **「ナビと検索から外す」に留めた**。
4. **完全な Zig パーサを書く** — ドキュメント生成に必要なのは宣言の「形」だけで、
   意味解析は `zig build test` の仕事。**行スキャナで十分**（文字列・文字リテラル・
   コメントを追跡してブレース深さを数える）。

## 4. 結果

* `zig build docs` が **183 ページ / 90 API ページ / 2,356 公開宣言（+ 内部 290）** を生成し、
  全リンク・全アセット・全アンカーを自分で検証する。
* ドキュメントコメントの無い宣言は「未文書」と明示され、パッケージページに
  **カバレッジ（文書化率）** が出る。数値は改善対象として可視化される。
  再エクスポート（`pub const X = y.Z` / `@import`）は文書化率の分母から除外する。
* 読者は「はじめに → ガイド → API」で完結し、内部資料は意図的に 1 クリック奥にある。

## 5. 副作用・制約

* **生成物はコミットしない**。`docs/api/**` は `./zigw build docs` の出力で、
  `.gitignore` 済み。したがって GitHub 上で `docs/api/…` を直接踏むことはできない
  （`check-docs.py` はそのパスだけリンク検査の例外にしている）。
* スキャナは Zig の文法を**部分的にしか**知らない。`comptime` で生成される宣言
  （`pub fn App(comptime mode) type` の中身など）は、その型を**使う側のファイル**には
  現れないので載らない。必要になったら「インスタンス化した型を渡す」拡張を足す。
* 文書化率は現時点で 21%。**未文書の宣言が 4/5 残っている**という事実を隠さない。
  API ページにそれが見えるので、次の増分の対象が機械的に決まる。
