# Security — deny by default

> **Audience**: readers about to ship, who want to know what is and is not protected.
> **Time**: 5 minutes.

Tauri's security model centres on **capabilities**. ziggurats implements it as-is: **a command that no
capability grants cannot be called from the frontend.**

## 1. Three layers

```text
  ① the WebView sandbox
     the boundary the OS provides. ziggurats does not touch it (same as a bare WebView)

  ② capabilities (ACL)      ← implemented by ziggurats
     "window `main` may call plugin:fs|read_text_file"
     decided by permission name + scope (which path). deny by default

  ③ CSP and headers         ← generated by zts_web
     script-src hashes, X-Frame-Options, COOP/COEP, …
```

## 2. Writing a capability

Same JSON as Tauri. Existing projects are read **unchanged**.

```json
{
  "identifier": "main-capability",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "fs:allow-read-text-file",
    {
      "identifier": "fs:scope",
      "allow": [{ "path": "$APPDATA/**" }]
    }
  ]
}
```

On the Zig side you load it and ask.

```zig
const imported = try tauri.config_import.load(allocator, io, "src-tauri");
defer imported.deinit();

var policy = try tauri.acl.Policy.init(allocator, .{
    .files = imported.capabilities,
    .platform = .linux,
});
defer policy.deinit();

if (!policy.allows("plugin:fs|read_text_file", "main", "tauri://localhost")) return error.Forbidden;
```

> [!WARNING]
> **An empty scope makes `fs` fail every time.** It is not "broken", it is denied, and the error
> reads `forbidden path`. Always write a glob such as `$APPDATA/**`.

### Per-permission scopes (`@tauri-apps/plugin-fs` compatible)

Each `permissions[]` entry may carry `allow` / `deny`. ziggurats attaches **only the scopes of the
capabilities that granted this call** to `rpc.Ctx`, and `plugin:fs|*` evaluates them when resolving
a path.

```json
{
  "identifier": "main-capability",
  "windows": ["main"],
  "permissions": [
    { "identifier": "fs:allow-read-text-file", "allow": [{ "path": "$APPDATA/**" }] },
    { "identifier": "fs:allow-write-text-file", "allow": ["$APPDATA/**"],
      "deny": ["$APPDATA/private/**"] }
  ]
}
```

| Rule | Behaviour |
|---|---|
| matches a `deny` glob | always rejected (`deny` wins over `allow`) |
| has one or more `allow` patterns, none match | rejected (`OutOfScope`) |
| an unscoped permission also grants the command | no restriction (same as Tauri's `CommandScope`) |
| no capability matches | `Policy.allows()` is already `false` |

Evaluation lives in `src/tauri/acl.zig` (`scopeAllowsPath` / `scopeAllowsUrl`). It is **combined
with** the config-derived `FsScope` roots: failing either check denies the call.

## 3. What is protected, what is not

| Protected | Not protected |
|---|---|
| commands absent from a capability | the frontend JavaScript itself (XSS is the WebView's job) |
| paths outside a scope | attackers over the network (CSP and server config) |
| warnings for unknown permission names | vulnerable dependencies |
| wrongly typed permissions (error) | OS-level permissions (filesystem ACLs) |

Listing the gaps is the same stance Tauri takes. **Not over-promising** is part of being safe.

## 4. CSP and headers

`zts_web` builds the CSP from the embedded assets. Inline scripts get **hashes**; `unsafe-inline`
is never used.

| Header | Default | Meaning |
|---|---|---|
| `Content-Security-Policy` | generated | hashes in `script-src`, `default-src 'self'` |
| `X-Frame-Options` | `DENY` | cannot be framed |
| `Cross-Origin-Opener-Policy` | off | enabled by `cross_origin_isolated = true` |
| `Content-Type: application/wasm` | static site | written into `_headers` (Cloudflare / Netlify) |

Some headers do nothing on desktop (the WebView does not go through HTTP). **The set that
applies depends on the artefact** — keep that in mind.

## 5. Checklist

Five things to check before shipping.

1. Capabilities grant **only** what is needed (no reflexive `core:default`).
2. `fs` scopes are narrow, such as `$APPDATA/**`.
3. No `unsafe-inline` / `unsafe-eval` in the generated CSP.
4. `zts doctor` passes.
5. Unknown-permission warnings are watched in CI.

```bash
zts build && grep -r "unsafe-inline" zig-out/ || echo "no inline"
```
